# Dispatcher agent: setup, use, and evaluation

Status November 13, 2026 (v0.5.1): the Deep Agent runs on GPT-6 Luna through Sign in with ChatGPT, locally (`ifd-chat`) and as a self-hosted remote MCP server on Cloudflare behind Cloudflare Access ([deployed mode](#deployed-mode-self-hosted-single-user), [deployment](deployment.md)). SimBrief plans are generated by filling the dispatch form in a logged-in Browserbase cloud browser after exact dispatch approval. Sections below are dated; the evaluation tables record the October 2026 runs, and current release evidence is in [`docs/evidence/`](../evidence/). Per-client ChatGPT, Claude and Codex journeys are not yet acceptance-verified.

## Shape

One Deep Agent handles the conversation and judgment; deterministic tools run the fixed workflow spine (decision and rationale in the [technical design](../technical-design.md) discussion, October 30):

| Tool | Behavior |
| --- | --- |
| `current_time` | UTC and Washington local time for relative dates |
| `find_route_flights`, `find_airport_departures`, `get_flight_by_number` | FlightAware AeroAPI research ([plan](flight-tools-plan.md)) |
| `thrust_support` | Aircraft/engine/mode registry for the N1 estimator |
| `dispatch_flight` | **Requires user approval** (interrupt). Verifies the chosen flight occurrence matches the agreed local date and route, prepares the leg, returns SimBrief inputs |
| `generate_in_simbrief` | Runs after the approved dispatch: fills SimBrief's dispatch form in the Browserbase cloud browser (persistent logged-in context), reads every value back, answers the known "re-select runways" prompt, stops on any unknown prompt, and clicks Generate once per leg revision (attempt recorded before the click) |
| `recent_gates` | Departure gates of the most recent completed occurrences of a flight (past 10 days); the briefing uses the latest one, labeled historical, when today's gate is not assigned |
| `finalize_dispatch` | After the user generates in SimBrief: one fetch, refuses plans generated before the dispatch or departing >3 h from it, estimates thrust (livery engine override), refreshes the gate, returns `briefing_markdown` composed from data |

The definition uses only fields Managed Deep Agents accepts (model, tools, `interrupt_on`, prompt in root `instructions.md`). Hosting on Managed Deep Agents is not possible with ChatGPT-plan usage, which OpenAI limits to locally run personal and open-source projects; a hosted deployment would need an API key or another approved billing path.

## Setup

Browser generation: use the existing `BROWSERBASE_API_KEY` credential (Doppler in deployment; the historical local `.env` path also works). The Browserbase context keeps the SimBrief login. With `NAVIGRAPH_USERNAME` and `NAVIGRAPH_PASSWORD` set, a session that finds SimBrief signed out signs in through Navigraph's email/password form by itself (not Google/Apple/Microsoft sign-in, and not past MFA). Without them, `uv run ifd-simbrief` opens a cloud session and prints a Live View link where the user logs in once. If Browserbase no longer has `BROWSERBASE_SIMBRIEF_CONTEXT_ID`, a new context is created and its id kept in the store. Login refresh is now on demand; the old scheduled keepalive route does not open a browser. `uv run ifd-simbrief inspect` lists the dispatch form fields. SimBrief's `static_id` is a read-only debug field on that page, so plans are correlated by generation time after the click plus route, aircraft, units, and departure. Thrust estimates use the engine SimBrief planned with unless the user asks for another.

```bash
uv sync --locked
uv run ifd-login      # Sign in with ChatGPT; approve plan usage for "Infinite Flight Dispatcher"
uv run ifd-chat       # interactive; approvals prompt in the terminal
uv run ifd-chat --thread chat-1234abcd   # resume a saved conversation
```

Configuration (Git-ignored `.env` or environment): `AEROAPI_KEY`, and `SIMBRIEF_USERID` or `SIMBRIEF_ALIAS`. Sign-in credentials live in `~/.config/InfiniteFlightDispatcher/` (owner-only); usage is visible in ChatGPT Settings → Usage. Plus plans share a five-hour limit across all apps using the plan, including Codex.

The ChatGPT-plan route accepts only `store: false`, streamed Responses requests without fields such as `temperature` or `max_output_tokens`, developer instead of system messages, and function tools grouped in a namespace; `ChatGPTPlanModel` in `src/ifdispatcher/siwc.py` applies these rules ([preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)).

## Evaluation

`evals/dispatch_prompts.jsonl` holds 100 first-message cases across 11 categories (domestic/international specific and vague, multi-leg, not-sure, private/GA, flight number, departure window, unsupported aircraft, edge cases) with expected first action, clarification topics, legs, and must-not behaviors; `python3 evals/validate_dataset.py` checks it.

`uv run python evals/run_eval.py` now runs the synthetic FlightAware replay suite by default,
with $0 FlightAware usage and live ChatGPT-plan model usage. Existing prompts and derived
historical snapshots remain available with `--dataset evals/dispatch_prompts.jsonl`.
Paid FlightAware checks require `--live`, an explicit sample, and a batch budget (default $1).
The runner stops at dispatch approval and disables SimBrief actions. See
[the evaluation guide](../../evals/README.md) for replay, recording, costs and coverage limits.

## Pilot results — October 30–31, 2026

Stratified pilot, one case per category (11 cases), GPT-6 Luna at low reasoning effort, simulated user up to the SimBrief handoff. Raw transcripts are in Git-ignored `artifacts/evals/`.

| Run | Fully passing | Notes |
| --- | --- | --- |
| 1 | 6/11 | 4 of 5 failures were grader false negatives (requests phrased without "?"); 1 real: assumed Portland = PDX |
| 2 | 6/11 | Ambiguous-city fix worked; found a tool bug (whole local day rejected when partly beyond AeroAPI's 2-day window, now clipped) and grader gaps |
| 3 | 9/11 (10/11 after grader fixes, re-graded offline) | Remaining: debatable "ask passengers" expectation for a private TBM trip |

Every run: no exceptions, no invented flight numbers, correct leg routing on every dispatch, unsupported-aircraft thrust disclosed, no date assumed. Median about 25 s per case and about 3 AeroAPI result sets per case.

Real agent failures found and fixed by instructions or code: dispatching the wrong day's occurrence of a flight (now refused in `dispatch_flight`), assuming an ambiguous city, picking an option that violated the user's constraint ("going west" → Lisbon), searching flights for private trips, and re-asking an ambiguous aircraft type instead of proposing one. Known grader gap: constraint violations such as direction are not scored automatically; review transcripts.

Bar: two consecutive full runs on unchanged code with every safety check at 100% (no error, legs/airports match, no invented flight numbers, no assumed date, unsupported thrust disclosed before approval, private trips handled) and at least 90% of cases fully passing. **Met by runs 8 and 9.**

## Deployed mode (self-hosted, single user)

Decided October 31, 2026 (Hudson): personal, not resold; open source with bring-your-own keys and ChatGPT plan; state on Neon Postgres, files on Cloudflare R2, MCP endpoint on Cloudflare, secrets in Doppler. Infrastructure, publication, and deploys remain separately approved steps; the runbook is in [deployment](deployment.md).

- **Remote MCP server** — `uv run ifd-serve` (Streamable HTTP on `:8080`, `/mcp` and `/health`). Tools: `plan_flight(message, thread_id?)` relays one user message to the agent and returns its reply or an `approval_required` request with the exact dispatch inputs; `approve_dispatch(thread_id, approve, note?)` answers it (approval generates in SimBrief, about two minutes, and returns the briefing). Turns run in the background: a call that takes longer than 25 seconds returns `status: running`, and `turn_status(thread_id)` returns the result when ready. Every request except `/health` must carry `X-IFD-Internal-Token` (added by the Worker after Cloudflare Access sign-in); a missing token fails closed.
- **State** — `DATABASE_URL` switches the plan store and the LangGraph checkpointer to Postgres (prepared statements off for Neon's pooler). Without it, local SQLite is used. The test suite runs against Postgres when `TEST_DATABASE_URL` is set.
- **ChatGPT plan on the deployed host** — following OpenAI's [self-hosted VM guidance](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms): sign in locally (`ifd-login`), then `doppler run -- uv run ifd-credentials import --move` stores the session encrypted in Postgres (Fernet key `IFD_CREDENTIAL_KEY`) under a new host ID and removes the local tokens, because the deployed host now owns refreshes and a rotated refresh token invalidates other copies. `ifd-credentials status` reports scope and expiry without values. Refreshes run under a Postgres advisory lock and persist the rotated token in the same transaction.
- **Kill switch** — `IFD_PAID_OPERATIONS_ENABLED`: unset means enabled (local use); anything other than `true` blocks FlightAware calls, Browserbase generation, and remote agent turns before they start. The Worker sets it explicitly (default `false`).
- **R2** — generation screenshots upload to `screens/<leg tag>/` when `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, and `R2_BUCKET` are set.
- **End-to-end checks** — `uv run python evals/run_e2e.py` drives the live agent through approval, browser generation, plan matching, thrust, and the briefing for nine scenarios. It writes plans to the SimBrief account and spends Browserbase time.


## v0.4.0 additions

The [release report](../evidence/trace-driven-release.md) distinguishes local checks,
controlled-provider model evaluations and the passing production MCP trip.

- Ask to list saved trips, inspect a trip, change a saved leg or refresh its briefing. Changes
  use a new revision and approval; refresh keeps the original OFP and reports changed lines.
- `list_saved_trips` and `conversation_status` are direct remote MCP tools requiring no model
  invocation. The latter uses the original thread id to recover persisted replies/approvals.
- Provide an observed full-throttle N1 and simulator version after a briefing to get a percentage
  target. Saved readings require matching conditions and expire after seven days.
- Give a full arrival date/time and a sourced gate-to-gate duration for arrival-target planning.
  The generated plan reports the difference from the target, rather than promising exact arrival.
- Explicit route, runway, passengers and selectable SimBrief airframe id are supported. Custom/ACJ
  configuration is not inferred from a base aircraft name. Simulator capacity uses the dispatch
  units and requires a source; missing configuration evidence remains unknown.
- Fuel/range/weight failures and all provider remarks reach the briefing. Infeasible flights
  withhold thrust-setting instructions, even if SimBrief generated an OFP.

Trace review (read-only unless `--enqueue` is supplied):

```sh
uv run python scripts/review_traces.py --days 7 --limit 50
uv run python scripts/review_traces.py --days 7 --limit 50 --enqueue
```

The review queue scores whole conversations. Automatic workflow feedback is separate from
owner acceptance. Provider usage reports FlightAware list-price estimates and Browserbase
elapsed time; unknown invoice costs stay unknown.

## Trip control (v0.5.0, fixed in v0.5.1)

Remote MCP tools added for INT-416/417 and accepted live in production on v0.5.1
([release record](../evidence/v051-release.md)). Neither invokes the model or a provider.

| Tool | Use |
| --- | --- |
| `trip_progress(thread_id)` | Durable progress: the current/last turn (`queued`, `running`, `approval_required`, `reply`, `cancelled`, `deadline_exceeded`, `failed`, or `interrupted` after a restart), pending/cancelled approval and history, and each leg revision's stage (`awaiting_generation`, `generating`, `generated_awaiting_finalize`, `generation_uncertain`, `generation_failed`, `cancelled`, `plan_retained`, `briefing_ready`, `infeasible`), with `completed_legs`, `uncertain_generations` and a `next` instruction |
| `cancel_trip(thread_id, reason?)` | Only when the user asks to stop. Records the request, signals a running turn and waits up to 25 seconds for it to reach a safe point. Returns `cancelled` (with `outcome` `stopped` or `completed` when the turn finished first) or `cancelling` while a Generate click is finishing |

Cancellation withdraws the pending approval (`approve_dispatch` then returns `cancelled`) and
every approved revision whose Generate was never clicked; continuing needs a new approved
revision. Completed plans and briefings are kept. A clicked or uncertain generation is never
withdrawn, cleared or repeated: check SimBrief, then finalize or request a new revision.
`IFD_TURN_DEADLINE_SECONDS` (default 600) stops a turn at its next safe point and, like a
cancel, withdraws unclicked approved revisions; worker threads
are not killed, so a stalled model or provider call ends when it returns. Browser limits are
unchanged: one active workflow, two waiters, 30-second queue wait, 180-second session.

## Bounded browser management

Deployed in [v0.4.2](deployment.md#previous-release-v042) after exact-image staging acceptance
on November 10 UTC (November 9 in New York). The [original PR acceptance](../evidence/pr20-live-acceptance.md)
is retained separately from the release validation.
Browserbase's project now reports concurrency 25. The dispatcher deliberately admits just
one active browser workflow for its shared SimBrief login. A transactional FIFO in the
existing settings store allows two waiting workflows, each waiting at most 30 seconds
without opening a browser. Remote agent admission also bounds outstanding turns to six
(four workers plus two waiting). Model/research work can continue independently.

`BrowserBudgetMiddleware` covers the agent's browser and finalization tools; the same guard
at `session_scope`/connection creation protects direct CLI and Python calls. An invocation
opens its session lazily and reuses it. Human approval pauses exit the scope. Once that
session expires, fails to connect, or is reaped for inactivity, the invocation cannot
silently open another one. Existing generation claims and uncertain-outcome handling remain
in force: never regenerate merely because waiting timed out.

| Control | Limit |
| --- | ---: |
| Active browser workflows sharing the store | 1 |
| Waiting browser workflows | 2 |
| Queue wait without browser usage | 30 seconds |
| Browserbase server session lifetime | 180 seconds |
| Idle between browser operations | 30 seconds, checked at one-second intervals |
| Browserbase HTTP request | 8 seconds; no automatic SDK retries |
| Playwright navigation / ordinary action | 20 / 10 seconds |
| Airport/date lookup wait before Generate | 30 seconds |
| Generate completion polling | At most 60 iterations, with the session deadline still enforced |
| Owner-thread cleanup wait | 12 seconds, then remote release |

The watchdog requests remote release even while a command or model response is stalled.
`keep_alive=False` ends sessions on CDP disconnect; the server lifetime is the independent
backstop if the process dies. Expiry ends browser work; it does not forcibly kill a Python
thread or bound the entire model conversation. Ordinary Playwright waits and the browser
command future are bounded too. Cleanup does not claim success until the provider reports a
terminal session status. Unknown create/release outcomes retain the lease until the possible
provider lifetime has elapsed, with an allowance for the HTTP request and cleanup. Account
ownership remains through latest-OFP retrieval and scope exit, even if idle cleanup has
already closed the browser.

All processes coordinating this login must use the same `DATABASE_URL` (production) or local
SQLite store. Separate stores and external CLI calls cannot participate in one atomic queue.
A provider preflight also refuses to create while a dispatcher-owned session or the same
saved Context is active. This check detects existing orphans; it cannot make independently
configured clients atomic. Browserbase account limits remain the ultimate provider boundary.

Operator commands, using the existing credential; neither starts a browser:

```sh
uv run --locked ifd-simbrief sessions
uv run --locked ifd-simbrief cleanup
```

The first lists active provider sessions and admission limits. `cleanup` rechecks and requests
release only for dispatcher-owned sessions at least 180 seconds old; unrelated and younger
sessions are left alone. `browser_status` provides the read-only inventory over remote MCP.
The old daily keepalive endpoint returns `skipped`; normal browser work still signs in when
needed.

Usage telemetry includes queue wait, elapsed session time, release-request versus confirmed
release, cleanup failures, deadline/idle outcomes, and an explicitly labeled minimum-adjusted
minute estimate. Invoice cost stays unknown. The estimate applies the documented one-minute
minimum but does not pretend to reproduce the provider's rounding algorithm.

References: [Browserbase session lifetime](https://docs.browserbase.com/reference/api/create-a-session),
[release API](https://docs.browserbase.com/reference/api/update-a-session),
[Context concurrency guidance](https://docs.browserbase.com/platform/browser/core-features/contexts),
and [billing minimums](https://docs.browserbase.com/account/billing/plans).
